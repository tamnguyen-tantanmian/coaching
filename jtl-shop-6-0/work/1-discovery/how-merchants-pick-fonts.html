JTL-Shop 6.0 · Theme Builder · Decision Paper

How merchants pick fonts

Three ways to wire typography into the theme builder. All three give merchants exactly the same freedom — they differ in what happens afterwards, when the shop grows, rebrands, or asks the AI setup to propose a look.

A note on wording: Shopify calls these controls text presets. This paper calls them text styles, because in ARC-17 a preset already means a theme's named token variation — a different thing, one level up.

The problem we are fixing

The theme panel as designed today has four font dropdowns and no font control on individual heading levels. Choosing a display face for the hero forces that same face onto product card titles, where it is too heavy. The merchant's only remaining lever is size — so they shrink H3 to hide it, and the heading scale stops being a scale. Every option below fixes this. The question is which one.

OPTION 1

Font slots, text styles point at them

What Shopify ships today. Four named slots hold the actual typefaces. Each text style has a dropdown that points at a slot rather than picking a family directly.

Option 1 4 slots  ·  5 text styles  ·  pointer per style

Strengths

  • A shop can never load more than 4 families — the cap is structural, not a rule we police.
  • "Playfair + Inter" exists as one object, which is what AI setup and the Aurora / Meridian / Editorial theme presets need to reason about.
  • Rebrand is one edit, no matter how many levels use the face.
  • Same shape as the colour panel, which already works in slots.

Costs

  • Merchants must learn what a "slot" is before the panel makes sense.
  • Slot names are abstract — "Accent" means nothing until something points at it.
  • Debugging a wrong font means checking two places, not one.
OPTION 2

A font picker on every text style

Drop the slot layer. Each text style carries its own font picker and chooses a family directly. What you see is what you set.

Option 2 no slots  ·  5 text styles  ·  family chosen per style

Strengths

  • Nothing to learn. The control does what it looks like it does.
  • Fewest clicks for a first-time setup.
  • Simplest to build and to support.

Costs

  • No structural cap: five families is roughly 500 KB of font before any content paints.
  • No object represents a font pairing, so AI setup has to emit five unrelated choices instead of one considered pair.
  • A rebrand is one edit per level — and grows if sections get their own type settings later.
  • Different mental model from the colour half of the same panel.
OPTION 3

Slots, with a Custom escape hatch

The text-style dropdown lists the four slots and a Custom… item. Picking Custom opens a family picker and quietly files that family into a free slot. Merchants who never think about slots behave exactly as in Option 2; the structure is there for the ones who need it.

Option 3 4 slots  ·  5 text styles  ·  pointer or Custom…

Strengths

  • Keeps every structural benefit of Option 1 — cap, pairing object, one-edit rebrand.
  • Costs a first-time merchant nothing: Custom… behaves like Option 2.
  • The slot concept is introduced at the moment it becomes relevant — when the cap is reached — not on the first screen.

Costs

  • Most design work: two paths through one dropdown, plus the "all four slots are in use" state.
  • Auto-filling a slot is invisible magic unless the panel shows what happened.
  • Needs a clear way to rename, reassign, and free a slot.

RECOMMENDATION

Build Option 3

Option 3 gives the day-one experience of Option 2 and the long-run properties of Option 1. It costs more design time, and that is the only thing it costs.

  • 01The font budget has to be structural. We own the performance story for every shop on the platform. A cap we enforce by asking merchants nicely is not a cap.
  • 02AI theme setup needs pairings, not five choices. The Pflichtenheft puts AI-assisted setup in MVP. "Playfair with Inter" is a piece of typographic knowledge; five independent font fields have nowhere to store it.
  • 03One panel should teach one idea. The colour half already works in slots. Two models on one screen is a support cost we would pay forever.

If the group does not find those three arguments decisive, Option 2 is a reasonable and cheaper answer — it is not a mistake, just a different bet. What is not defensible is shipping today's mockup, because it fails a requirement rather than a preference.

TO DECIDE

What we need from this meeting

Which option do we build? Blocks the Figma variable structure and the theme data model. Everything downstream waits on this.
Is AI theme setup in the MVP? If it is out, argument 02 disappears and Option 2 becomes materially more attractive.
Do we accept a hard cap of four font families per shop? A yes makes the choice between Options 1 and 3 purely a UX question. A no rules both of them out.
